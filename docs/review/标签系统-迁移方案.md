## 一、迁移目标与范围

- **现状**：`Card.tags: string[]` 字符串内联（`types.ts:11`），无独立 Tag 实体、无 prompt_tags、无外键；存储为 `data/store.json` 单文件（`serverStore.ts` 进程内单例 + writeChain 落盘 + SSE 广播）+ localStorage 兜底（`storage.ts`）。
- **目标**：一次性迁移到「tags 实体 + prompt_tags 关联」的独立 ID 体系（对齐交接 §38 三表结构），为 P0 的树形 / 重命名 / 移动 / 全局操作打地基。
- **数据规模**：32 卡 / 56 条 tag 条目 / 去重 14 标签 / 3 处脏数据 → **推荐一次性全量迁移，无需增量**。
- **迁移后实体数**：14 − 3（多age、多aengt 并入）+ 0（无法分类 删除）− 1（多agent编程 保留合并目标）= **11 个标签实体**。

## 四、迁移脚本伪代码（含 dry-run 报告）

> 执行形态：一次性 Node 脚本，**默认 dry-run**，加 `--apply` 才落盘；落盘前自动生成 `data/store.json.bak-YYYYMMDD-HHMMSS`。

```ts
// scripts/migrate-tags.mjs（伪代码，第 3 步实现时落真）
const MERGE: Record<string, string | null> = {
  '多age': '多agent编程',       // 截断碎片 → 完整名
  '多aengt编程': '多agent编程',  // 错别字 → 正确名
  '无法分类': null,             // DISCARD 占位 → 删除
}

function dryRun(raw: ServerState) {
  const freq = new Map<string, number>()          // 合并后 标签名 → 频次
  const cardTagCount = new Map<string, number>()  // 卡片 id → 关系数（校验用）
  for (const c of raw.cards) {
    const seen = new Set<string>()                // 卡内去重（防同一卡多age+多agent编程双份）
    for (const t of c.tags) {
      const target = MERGE[t] ?? t
      if (target === null) continue               // 删除类
      freq.set(target, (freq.get(target) ?? 0) + 1)
      if (seen.has(target)) warn(`卡 ${c.id} 合并后标签重复: ${target} → 已去重`)
      seen.add(target)
      cardTagCount.set(c.id, (cardTagCount.get(c.id) ?? 0) + 1)
    }
  }
  // 按频次降序 + 名称排序 → 分配 tag_001…
  const ordered = [...freq.entries()].sort((a, b) => b[1] - a[1] || a[0].localeCompare(b[0], 'zh'))
  const tags = ordered.map(([name, n], i) => ({ id: `tag_${String(i + 1).padStart(3, '0')}`, name, ... }))
  // 生成 promptTags（二次遍历卡片，用 name→id 映射）
  return { tags, promptTags, report }
}

function apply() {
  const raw = readStore()                       // 读 data/store.json
  const { tags, promptTags, report } = dryRun(raw)
  backup(`${DATA_FILE}.bak-${timestamp}`)       // 1. 备份
  writeStore({ ...raw, version: 2, tags, promptTags })  // 2. 落盘新结构
  printReport(report)                           // 3. 报告
}
```

## 五、存量 Card.tags 保留 / 删除取舍与 isCard 变更

| 方案 | 做法 | 优点 | 风险 | 结论 |
|---|---|---|---|---|
| **A. 保留冗余（推荐）** | 迁移后 `Card.tags` 字段保留（改为合并后的标签名数组，与新结构同步维护），`isCard`（`storage.ts:22-40`）**不改** | ① 旧客户端（未升级页面）经 `loadFromServer` 的 `isCard` 过滤仍能读到卡片，不会丢数据；② localStorage 离线兜底兼容；③ 卡片导出 Markdown（`storage.ts:248-276` 的 `标签：` 行）不变 | 双写维护成本；tags 与 promptTags 可能短暂不一致（写入顺序保证先 promptTags 后 tags 或事务式整体替换即可避免） | **选 A** |
| B. 删除字段 | `Card.tags` 移除，`isCard` 改为 tags 可选（`x.tags === undefined \|\| isStringArray(x.tags)`） | 单一事实来源，无双写 | **旧客户端全量丢卡**（`loadFromServer` 里 `isCard` 过滤整卡丢弃）；导出格式需改；回滚更复杂 | 不推荐 |

**isCard 变更建议（方案 A）**：`storage.ts:29` 的 `isStringArray(x.tags)` 保持原样；仅当将来决定收紧/放开上限时才动。新结构校验新增两个守卫（仅服务端 `serverStore` 层）：

```ts
const isTag = (v: unknown) => v && typeof v === 'object'
  && typeof (v as Tag).id === 'string' && typeof (v as Tag).name === 'string'
const isPromptTag = (v: unknown) => v && typeof v === 'object'
  && typeof (v as PromptTag).prompt_id === 'string' && typeof (v as PromptTag).tag_id === 'string'
```

> 交接 §37「标签不要写入 Prompt 正文」：`Card.tags` 是元数据字段，非 `body` 正文，保留字段不违反该约束。

## 六、关系层放置与外键安全约束

### 6.1 放置位置

- 新增 `tags` / `promptTags` 集合进 `data/store.json`，由 **`serverStore.ts` 同层**管理（沿用现有进程内单例 + `writeChain` 串行落盘 + EventEmitter/SSE 版本广播，`serverStore.ts:18-68`）。
- 新增标签变更入口统一封装在 `serverStore` 的 mutation 函数中，**禁止任何调用方绕过 mutation 直接改内存/文件**，从结构上保证约束不旁路。

### 6.2 应用层外键约束（无数据库时的安全等价物）

交接 §40 方向：`Tag 删除 → 允许级联删除 PromptTag → 绝不级联删除 Prompt`。在 JSON 存储下用**操作顺序 + 封装**模拟：

```ts
// 删除标签（安全顺序）
async function deleteTag(tagId: string) {
  // 1. 先删 promptTags 中所有 tag_id === tagId 的关系（级联关系）
  state.promptTags = state.promptTags.filter(rt => rt.tag_id !== tagId)
  // 2. 再删 tags 实体
  state.tags = state.tags.filter(t => t.id !== tagId)
  // 3. 绝不触碰 state.cards（Prompt 一条不删）—— 硬约束
  await commit() // writeChain 落盘 + version+1 + SSE 广播
}

// 添加/更新卡片标签（原子：整体替换该卡关系）
async function setCardTags(promptId: string, tagIds: string[]) {
  state.promptTags = [
    ...state.promptTags.filter(rt => rt.prompt_id !== promptId),
    ...unique(tagIds.map(tagId => ({ prompt_id: promptId, tag_id: tagId }))), // 唯一约束
  ]
  await commit()
}
```

**唯一约束**：`(prompt_id, tag_id)` 由 `unique()` 强制（写入前去重 + 覆盖式整体替换），等效 SQL `UNIQUE(prompt_id, tag_id)`（交接 §38 末尾）。

## 七、回滚方案与数据完整性验证

### 7.1 回滚步骤（迁移失败 / 验收不通过时）

1. **停服**：`./dev-server.sh stop`（防止落盘/SSE 写回覆盖）。
2. **恢复 store.json**：将 `data/store.json.bak-<timestamp>` 复制回 `data/store.json`（迁移脚本 `--apply` 前自动生成，沿用现有 `.bak` 先例）。
3. **清理 localStorage 第二副本**：旧页面若已推送过 v2 结构，localStorage（`prompt-manager:cards` / `prompt-manager:settings`）可能含新结构 → 在浏览器控制台执行 `localStorage.clear()` 或删除两个 key，重启后从服务端重新拉取旧结构。
4. **重启**：`./dev-server.sh start` → 浏览器访问确认 32 卡 / 14 旧标签均恢复。
5. **验证**：卡片数、标签数、正文内容与回滚前快照一致（对照 §7.2 校验脚本输出）。

> 由于 localStorage 是「离线兜底 + 推送源」，恢复顺序必须是「先恢复服务端文件，再清客户端缓存」，否则旧 localStorage 会把旧结构又推回服务端（无害但会覆盖恢复结果）。

### 7.2 数据完整性验证（迁移后必须执行）

```ts
function validate(state: ServerState): string[] {
  const errors = []
  const tagIds = new Set(state.tags.map(t => t.id))
  const promptIds = new Set(state.cards.map(c => c.id))
  // ① 关联数一致性：promptTags 数 === 各卡合并后 tags 总和
  const cardSum = state.cards.reduce((s, c) => s + new Set(c.tags).size, 0)
  if (state.promptTags.length !== cardSum) errors.push(`关联数不一致: promptTags=${state.promptTags.length} vs cards.tags=${cardSum}`)
  // ② 无孤儿关系：每个 promptTags.tag_id 必须存在于 tags
  for (const rt of state.promptTags)
    if (!tagIds.has(rt.tag_id)) errors.push(`孤儿关系: ${rt.prompt_id}→${rt.tag_id}`)
  // ③ 无孤儿标签：每个 tags 至少 1 条关系（未使用标签允许但需报告）
  // ④ 唯一约束：promptTags 无重复 (prompt_id, tag_id)
  // ⑤ 卡片完整性：cards 每条仍有合法 id/body（isCard 全过）
  // ⑥ 引用完整：promptTags.prompt_id 均存在于 cards
  return errors // 空 = 通过
}
```

**预期通过基线**：promptTags=55、tags=11、孤儿=0、重复=0、isCard 全过。

## 八、树循环检测与重名检测实现要点（P0 第 3 步建树时启用）

### 8.1 树循环检测（交接 §43 四条禁令）

```ts
// 设置 parent_id 前的守卫（createTag / moveTag / renameTag 统一走此校验）
function assertNoCycle(tags: Tag[], tagId: string, newParentId: string | null): boolean {
  if (newParentId === null) return true
  if (newParentId === tagId) return false                      // ① 不能成为自己的父
  const children = new Set(tags.filter(t => t.parent_id === tagId).map(t => t.id))
  if (children.has(newParentId)) return false                  // ② 不能移到自己的子节点
  // ③ 环检测：沿 newParentId 向上溯祖，若途经 tagId 即成环
  let cur = newParentId
  const guard = new Set<string>()
  while (cur !== null) {
    if (guard.has(cur)) return false                           // 数据异常兜底
    guard.add(cur)
    if (cur === tagId) return false                            // ③ 成环
    cur = tags.find(t => t.id === cur)?.parent_id ?? null
  }
  return true
}
```

- 三个入口统一拦截：创建、移动、重命名父级。
- 追加约束：`tag_id === parent_id` 在存储层再验一遍（纵深防御，即使 UI 绕过）。

### 8.2 重名检测（交接 §28/§30/§43：同父级下唯一）

```ts
// 同一 parent_id 下 name 唯一；不同父级允许同名（交接 §29），UI 显示完整路径
function assertNameUnique(tags: Tag[], parentId: string | null, name: string, excludeId?: string): boolean {
  return !tags.some(t => t.id !== excludeId && t.parent_id === parentId && t.name === name)
}
```

- 触发点：创建标签、标签重命名、标签移动（移到新父级时校验该父级下是否重名）。
- 与现有「无独立标签创建入口」的差异：当前字符串内联下无任何检测（审计 §四 P0-18 ❌），迁移后由实体层强制。
