# 风险登记（risks）

> 从 `docs/handoff/HANDOFF.md` 迁出。每条给出「现象 / 成因 / 当前处置 / 何时升级」。最后核对：2026-10-31。

## R1｜离线 MCP 包是快照，不随库更新

- **现象**：访客装好后，你在库里改了卡片或新增调取码，他那边不变。
- **成因**：静态站没有服务端，只能把卡片正文内嵌进本地文件。
- **处置**：面板与文档已写明「重新复制一次即可覆盖，客户端不用重配」。
- **升级条件**：若需要「改完立刻生效」，必须走联网版（服务端可被对方访问 + 设备令牌）。

## R2｜模型可能不去调工具（依赖客户端常驻说明）

- **现象**：用户说「调取 hi」，模型先 `rg` 搜文件、或当成问候回一句。
- **成因**：MCP 工具描述会被模型忽略；不同客户端注入力度不同。
- **实测结论**：`codex 0.164.0` 在**有常驻规则**（`AGENTS.md`）时连跑 3 次全中；只有工具描述时不稳定。
  主推话术从「调取 hi」改为 **「调取码 hi」** 后明显更稳。
- **处置**：安装流程第 6 步要求把规则写进客户端常驻说明（Codex/opencode 的 `AGENTS.md`、
  WorkBuddy 记忆文档、Cursor 的 rules）；完成标准含「新会话只说几个字也能触发」。
- **剩余风险**：客户端不提供常驻说明机制时（如部分网页端），只能靠用户说「调取码 xxx」提高命中。

## R3｜账本机器校验存在存量失败（阻断账本入库）

- **现象**：`node scripts/model/check-ledger.mjs docs/model` 返回 exit≠0，导致 `TASK-MODEL-LOG.jsonl`
  无法提交（pre-commit 拦截）。
- **成因（存量，非本轮引入）**：
  - `DISPATCH-LOG.jsonl` 有 6 处 `runtime` 用了枚举外写法（`本窗口subagent` / `本窗口直驱`）；
  - 2026-09-30 `TASK-P1-sync-loop` 同 task 在两本账里 result 口径不一致（dispatch=FAIL vs task=PASS，
    实为「打回后返工通过」，语义不同）。
- **处置**：按「禁改写历史实绩」，本轮未动这些行；本轮账本行**已落盘但未入库**。
- **升级条件**：治理批次里把历史 `runtime` 规范到枚举值、并按脚本指引为 09-30 那条另起一行更正，
  之后账本即可正常入库。

## R4｜卡片正文含 `</activated-instructions>` 会破坏激活包装

- **现象**：该字面量出现时，激活文本的闭合标签提前结束，后半段指令落到包装外。
- **成因**：`buildActivationText` 与既有联网版 MCP server 都是直接字符串拼接。
- **状态**：**既有行为，未修**。影响面仅限「用户自己的卡片正文恰好写了这个标签」。
- **升级条件**：若出现真实误用，改为对正文做转义或改用非标签式分隔。

## R5｜部署前打开的旧标签页会把主题打回 `system`

- **现象**：用户切到新主题后被旧客户端归一化回 `system`。
- **成因**：全量快照同步 + 旧版 JS 的 `normalizeSettings` 白名单不含新主题值。
- **处置**：用户需刷新/关闭所有旧标签页与旧设备页面；服务端无法区分「用户选 system」与「旧客户端归一化」。

## R6｜React #418 水合告警（回收站计数）

- **现象**：偶发 pageerror `#418`，与本轮改动无关。
- **处置**：未修。回收站初始化涉及「先毁后读」风险，需 `useState([])` + skip-first-write 守卫，
  不能直接改成 initializer 读 localStorage。

## R7｜静态产物可能误带真实数据（需每次发布前核一次）

- **检查方法**：用真实库里的独特标题在 `out/` 中 `grep -rl`，**必须 0 命中**；示例卡命中属预期。
- 现状：2026-10-31 用 5 个真实标题核过，0 命中。
- **升级条件**：任何时候新增「把库内容打进静态产物」的需求（如导出演示库），都要重跑此检查。
